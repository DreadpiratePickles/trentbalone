**The single most important framing shift:** in 2024–25 the question was "which orchestration framework?" In 2026 the question is "what does my harness own, what does my runtime own, and where does state live?" Anthropic states this explicitly — Managed Agents virtualizes three components, **Session** ("the append-only log of everything that happened"), **Harness** ("the loop that calls Claude and routes Claude's tool calls to the relevant infrastructure"), and **Sandbox** ("an execution environment where Claude can run code and edit files") — and each implementation can be swapped without disturbing the others ([Anthropic Engineering](https://www.anthropic.com/engineering/managed-agents)).

### 1.2 Orchestration patterns that survived contact with production

Independent 2026 write-ups converge on the same small set of topologies, and on the same anti-hype conclusion. The canonical set is **sequential/pipeline, parallel fan-out (scatter-gather), supervisor/orchestrator-worker, hierarchical (stacked supervisors), swarm/peer-to-peer handoff, debate/maker-checker, and blackboard** ([architecturediagram.ai](https://architecturediagram.ai/blog/multi-agent-orchestration-patterns), [munderdiffl.in](https://munderdiffl.in/blog/multi-agent-orchestration-patterns/)).

- **Supervisor / orchestrator-worker is the 2026 default.** One agent owns routing and delegates to specialised workers ([reactify-solutions](https://www.reactify-solutions.com/articles/multi-agent-orchestration-2026)).
- **The most important finding is negative:** "a **single agent often matches or beats** a multi-agent" setup ([munderdiffl.in](https://munderdiffl.in/blog/multi-agent-orchestration-patterns/)). Most production systems settle on a supervisor or a sequential pipeline; peer swarms remain a minority ([paiteq](https://www.paiteq.com/blog/multi-agent-orchestration-patterns/)).
- **The names differ but the wire is identical** across LangGraph, OpenAI Agents SDK, CrewAI, MAF and Anthropic's in-house stack ([reactify-solutions](https://www.reactify-solutions.com/articles/multi-agent-orchestration-2026)).

**The deterministic-backbone pattern is the one to copy.** CrewAI's framing is the clearest articulation: a **Flow** is "a deterministic backbone that owns the structure" — "a very thin code layer with almost no abstractions" defining which steps execute, in what order, with what guardrails — and intelligence is injected *selectively* at specific steps as a raw LLM call, a single agent, or a full Crew. Every intelligence component "must return control to the Flow when finished." The stated execution property: "Same inputs, same execution path." ([CrewAI](https://crewai.com/blog/how-to-build-agentic-systems-the-missing-architecture-for-production-ai-agents))

Google's ADK 2.0 made the same move structurally, from a hierarchical agent executor to a graph engine where "your Agents, Tools, and Functions are evaluated as individual *nodes* within a workflow graph" ([adk.dev](https://adk.dev/2.0/)).

### 1.3 What "well-architected" means, from the people who built the runtimes

LangChain's post-mortem on building LangGraph names **six features required to take agents to production**, and it is the best available checklist:

1. **Parallelization** — "to save actual latency"
2. **Streaming** — "to save perceived latency"
3. **Task queue** — "to reduce number of retries"
4. **Checkpointing** — "to reduce the cost of each retry"
5. **Human-in-the-loop** — "to collaborate with the user"
6. **Tracing** — "to learn how users use it"

…with low latency as an overarching constraint, because developers won't adopt a framework that delivers all six "at the cost of making their LLM app perceivably slower." Their design conclusion: "We aimed to find the right abstraction for AI agents, and decided that was little to no abstraction at all. Instead, we focused on control and durability." And the warning every framework vendor should have printed on the wall: **"The biggest competitor to any code framework is always no framework."** ([LangChain](https://www.langchain.com/blog/building-langgraph))

Two harness-layer patterns from OpenAI are worth internalising:

- **Harness/compute separation.** "Separating harness and compute helps keep credentials out of environments where model-generated code executes." Design assuming prompt-injection and exfiltration attempts. ([OpenAI](https://openai.com/index/the-next-evolution-of-the-agents-sdk/))
- **Externalized state + snapshot/rehydrate.** "Losing a sandbox container does not mean losing the run" — the SDK restores agent state in a fresh container and continues from the last checkpoint if the original environment fails or expires ([OpenAI](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)).

Anthropic's version of the same lesson is a pets-vs-cattle story: the initial server/container was a "pet"; decoupling containers from harnesses made both interchangeable "cattle." They also document a real failure mode worth designing for — **"context anxiety,"** where Claude Sonnet 4.5 "would wrap up tasks prematurely as it sensed its context limit approaching," which the harness addressed with context resets (and which Opus 4.5 no longer exhibited) ([Anthropic Engineering](https://www.anthropic.com/engineering/managed-agents)).

Microsoft's MAF harness is the most concretely enumerated: automatic context compaction that "monitors token usage" and "compacts chat history mid-loop," plus built-in providers — `FileMemoryProvider` (session-scoped file memory at `agent-file-memory/{session}/`), `FileAccessProvider`, `TodoProvider`, `AgentModeProvider` (`plan`/`execute` modes), `AgentSkillsProvider`, and `BackgroundAgentsProvider` for fan-out to parallel child agents ([Microsoft](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-at-build-2026-announce/)).

### 1.4 A2A — adoption status

- **Governance:** Google launched A2A April 2025, donated it to the Linux Foundation June 2025, IBM merged its Agent Communication Protocol into A2A August 2025, and on **August 17, 2026** A2A joined the **Agentic AI Foundation (AAIF)** alongside MCP. Framing that matters: "What changed this month is which foundation hosts the work, not who controls it… A shared foundation settles who stewards the specifications. It does not standardize enterprise authorization policy." ([Forbes](https://www.forbes.com/sites/janakirammsv/2026/08/19/agent2agent-joins-the-agentic-ai-foundation-alongside-mcp/))
- **Adoption metrics (April 9, 2026, one-year mark):** more than **150 supporting organizations** (up from 50+ in April 2025), **22,000+ GitHub stars**, SDKs in **five production-ready languages** (Python, JavaScript, Java, Go, .NET), and vertical adoption in supply chain, financial services, insurance, and IT operations ([Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)).
- **Cloud availability:** Microsoft integrated A2A into **Azure AI Foundry** and **Copilot Studio**; AWS added support via **Amazon Bedrock AgentCore Runtime**; Google integrated it across its platforms. "These integrations position A2A as a default standard for building agent-based systems in the cloud." ([Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year))
- **v1.0 spec** (first stable) added multi-protocol support, enterprise-grade multi-tenancy, modernized security flows, a migration path, and **Signed Agent Cards** with cryptographic identity verification ([Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)).
- **The honest read:** A2A "is not dead, but it is also not universally useful" — it earns its keep across *organizational* boundaries where agents span frameworks/vendors, and is overhead inside a single codebase ([glukhov.org](https://www.glukhov.org/ai-systems/comparisons/a2a-protocol-2026-adoption/)). Overlapping efforts persist: Cisco's AGNTCY covers similar discovery/identity ground ([Forbes](https://www.forbes.com/sites/janakirammsv/2026/08/19/agent2agent-joins-the-agentic-ai-foundation-alongside-mcp/)).

**Recommendation for a Next.js/TS shop:** you almost certainly do not need A2A internally. Adopt it only when you expose agents to, or consume agents from, another organization. Use MCP for tools, A2A for cross-org delegation.

### 1.5 MCP in production

**The `2026-07-28` specification is the biggest change since launch**, and it is a deployment-model change, not a feature release ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)):

- **Stateless core.** "MCP is transforming from a bidirectional stateful protocol into a request/response stateless protocol." The `initialize`/`initialized` exchange and the `Mcp-Session-Id` header are retired. "Any request can now land on any server instance behind a plain round-robin load balancer without needing shared storage." Each request carries protocol version, client identity and capabilities in `_meta`.
- **Header-based routing.** "Method and tool names travel in the `Mcp-Method` and `Mcp-Name` HTTP headers, so gateways can route and authorize on headers directly" — your WAF/rate limiter no longer parses JSON bodies.
- **MRTR replaces long-lived streams.** Server-to-client requests (sampling, elicitation) redesigned as **Multi Round-Trip Requests** (SEP-2322), "removing the need for constantly open bidirectional streams."
- **Cache-stable catalogs.** "List responses carry cache hints and a deterministic order, so clients can cache tool catalogs and keep upstream prompt caches stable across reconnects." This is a direct cost lever (see §2.5).
- **Extensions framework** formalized, with **Tasks**, **MCP Apps** (server-rendered UIs) and **Enterprise Managed Authorization (EMA)** as extensions.
- **Auth hardening:** RFC 9207 issuer validation and a formal shift from **Dynamic Client Registration (DCR)** to **Client ID Metadata Documents (CIMD)**. "DCR continues to work for backward compatibility, but will be removed in a future version of the MCP spec."
- **Deprecation policy:** "a formal deprecation policy with a twelve-month minimum window."
- **SDK scale:** four Tier 1 SDKs (TypeScript, Python, Go, C#) with "close to half-a-billion downloads a month"; the TypeScript and Python SDKs have each crossed **1 billion total downloads**. Rust supports the new spec in beta.

**Roadmap context** (published March 9, 2026) named four priority areas: Transport Evolution & Scalability, Agent Communication (Tasks lifecycle — retry semantics, result-retention expiry), Governance Maturation (contributor ladder, delegated SEP review), and Enterprise Readiness (audit trails, SSO-integrated auth, gateway behavior, config portability). Explicitly: "We are **not adding more official transports this cycle**." Named SEPs: **SEP-1686** (Tasks), **SEP-1932** (DPoP), **SEP-1933** (Workload Identity Federation). ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-mcp-roadmap/))

**The most important MCP production pattern of 2026 is Code Mode.** Instead of exposing N tools and burning context on schemas, expose *one* code-execution tool and let the model write code against a typed SDK. Cloudflare's implementation gives an agent "an entire API in 1000 tokens": a single MCP server for the whole Cloudflare API exporting just `search()` (searches the OpenAPI spec with `$refs` pre-resolved) and `execute()` (runs a JavaScript async arrow function against the API). Generated code runs in a **Dynamic Worker isolate** — "a lightweight V8 sandbox" with no file system, no environment variables to leak through prompt injection, and external fetches disabled by default; Workers OAuth Provider downscopes tokens so "the agent only gets the capabilities the user explicitly granted." ([Cloudflare](https://blog.cloudflare.com/code-mode-mcp/), [Code Mode docs](https://developers.cloudflare.com/agents/tools/codemode/))

Anthropic ships the equivalent as **programmatic tool calling** — Claude calls tools "from a code execution environment," keeping intermediate results out of context, which Vercel notes "can significantly reduce token usage and cost" ([Vercel AI SDK 6](https://vercel.com/blog/ai-sdk-6)).

## 2. Agent deployment & infrastructure

### 2.1 Where agents actually run

Four deployment shapes are in production, and the choice is driven by session duration and statefulness:

**(a) Durable-object / actor edge runtime.** Cloudflare's model: "each agent session has a durable identity, local SQL storage, real-time connections, scheduled work, and recoverable execution… No infrastructure to manage, no sessions to reconstruct, no state to externalize," scaling "to tens of millions of instances." Durable Objects became available on the free tier in July 2026 ([Cloudflare Agents](https://developers.cloudflare.com/agents/), [Cloudflare blog](https://blog.cloudflare.com/building-ai-agents-with-mcp-authn-authz-and-durable-objects/)).

**(b) Kubernetes with an agent-shaped primitive.** Kubernetes SIG Apps is building **Agent Sandbox**, "a declarative, standardized API specifically tailored for singleton, stateful workloads like AI agent runtimes." The problem statement is exact: an agent is an "isolated, stateful, singleton workload" needing persistent identity, "a secure scratchpad for writing and executing often untrusted code," and suspend/resume — which naively requires "a StatefulSet of size 1, a headless Service, and a PersistentVolumeClaim… for every single agent." The `Sandbox` CRD natively supports **gVisor** and **Kata Containers** for kernel and network isolation, scales idle environments to zero, and gives every Sandbox a stable hostname. Extensions include **SandboxWarmPool** (pre-provisioned pods to eliminate cold starts, since "a new pod adds about a second of overhead") and **SandboxClaim**/**SandboxTemplate**. ([Kubernetes blog](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox/))

There is an active architectural debate here: **kagent** made each agent a first-class K8s workload with its own Pod, Service and ServiceAccount after initially running many agents in one runtime; others argue for treating pods as *workers* rather than agents ([InfoQ](https://www.infoq.com/news/2026/08/pod-deployment-unit-ai-agents/)). Red Hat's **Kagenti** takes a zero-trust control-plane approach with a `Component` CRD ([Red Hat](https://next.redhat.com/2026/03/05/zero-trust-ai-agents-on-kubernetes-what-i-learned-deploying-multi-agent-systems-on-kagenti/)).

**(c) Managed agent runtime (agent-as-a-service, first-party).** Anthropic's **Claude Managed Agents** (public beta, announced April 8, 2026) is "a suite of composable APIs for building and deploying cloud-hosted agents at scale," pairing an Anthropic-managed harness with production infrastructure for state, memory, permissions and scheduled execution — including sandboxed code execution, checkpointing, credential vaults, scoped permissions, MCP tunnels, self-hosted sandboxes and end-to-end tracing. Developers define tasks, tools and guardrails; Anthropic runs the loop. Multi-agent coordination and outcome definition/self-evaluation are in research preview. ([Anthropic](https://claude.com/blog/claude-managed-agents))

**(d) Serverless + durable workflow.** For a Next.js stack this is the pragmatic default: stateless HTTP handlers for the request path, a durable workflow engine for the agent loop. See §2.4.

### 2.4 Durable execution — the layer most teams are missing

Two mechanisms dominate: **journal-based replay** (record each completed step, replay on crash) and **database checkpointing** (persist state after each node) ([zylos](https://zylos.ai/research/2026-02-17-durable-execution-ai-agents/)).

The market crossed the chasm in 2026: "AWS, Cloudflare, and Vercel all shipped first-party" durable execution ([reptile.haus](https://reptile.haus/journal/durable-execution-ai-agents-temporal-restate-inngest-2026/)).

### 2.5 Cost optimization for multi-model agent fleets

The diagnosis is architectural, not price-list: 2026 cost overruns are "caused by agentic workflows that generate 5–30× (sometimes 100×) more tokens than chatbot interactions, combined with default-to-frontier routing and unbounded context" ([ssntpl](https://ssntpl.com/ai-agent-cost-optimization-model-routing-guide-2026/)).

**Lever ranking, highest leverage first** ([jobsbyculture](https://jobsbyculture.com/blog/llm-cost-optimization-guide-2026)):

1. **Prompt caching** — 60–80% cost cut on agent/chat workloads
2. **Model routing** — 50–70% cut on mixed workloads
3. **Batch API** — 50% cut on offline pipelines
4. **Output-shape engineering** — 20–40%

**Prompt caching is the highest-ROI single change, and it has peer-reviewed numbers.** The PwC paper *"Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks"* (arXiv:2601.06007v2, Jan 31 2026) evaluated GPT-5.2, GPT-4o, Claude Sonnet 4.5 and Gemini 2.5 Pro on DeepResearch Bench and found: **"prompt caching reduces API costs by 41-80% and improves time to first token by 13-31% across providers."** The actionable finding is cache-block discipline — "placing dynamic content at the end of the system prompt, avoiding dynamic tra[nsformations]" ([arXiv](https://arxiv.org/html/2601.06007v2)).

Provider mechanics differ and this matters for architecture: OpenAI caches automatically above a token threshold with exact-prefix matching; Anthropic uses developer-controlled explicit cache breakpoints with configurable TTL; Google offers implicit caching (no guaranteed savings) plus explicit context caching (guaranteed discounts) ([arXiv](https://arxiv.org/html/2601.06007v2)).

**Current cache economics (verified):**

- Anthropic: cache reads are normally **0.1× base input price**, but on Claude Fable 5.1 / Mythos 5.1 they are **$0.25/MTok = 0.025× base input** — "75% less than Fable 5, which reduces the cost of typical workloads by an estimated 25%" ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api), [Claude Fable page](https://www.anthropic.com/claude/fable)).
- OpenAI: cached input is 10% of base input across the GPT-5.6 family — e.g. `gpt-5.6-sol` at $4.00 input / **$0.40 cached** / $20.00 output per 1M tokens ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)).

**Model routing.** The pattern is a cheap classifier or heuristic in front of a tiered fleet: small models for deterministic low-risk work, frontier models where retry-and-review costs dominate ([therouter.ai](https://therouter.ai/blog/llm-api-cost-optimization-routing-strategies-2026/)). Reported savings cluster at **40–85%** with tuned routing ([digitalapplied](https://www.digitalapplied.com/blog/llm-model-routing-2026-cost-quality-optimization-engineering-guide)) and **50–70% with <2% quality loss** ([ailog](https://app.ailog.fr/en/blog/guides/llm-routing-cost-optimization)). Three strategies: complexity-based, cascade, and consensus routing ([ailog](https://app.ailog.fr/en/blog/guides/llm-routing-cost-optimization)).

**Gateways, verified:**

- **OpenRouter** — one OpenAI-compatible endpoint to 300+ models from 60+ providers; grew from $10M ARR (Oct 2024) to **$100M+ ARR by May 2025** (10× in seven months), $40M round at $500M valuation, 1M+ developers. `openrouter/auto` selects among dozens of models via Not Diamond's meta-model at no extra cost, plus provider fallback ([agentmarketcap](https://agentmarketcap.ai/blog/2026/04/08/agent-request-routing-multi-model-orchestration-litellm-openrouter), [zylos](https://zylos.ai/research/2026-03-02-ai-agent-model-routing/)). ### 3.3 Evaluation — frameworks vs benchmarks

Keep the distinction clean: **frameworks** are tooling you point at your own agent; **benchmarks** are fixed task sets with leaderboards ([Morph](https://www.morphllm.com/ai-agent-evaluation)).

**Frameworks.** `DeepEval` (Apache-2.0, pytest-style, 50+ research-backed metrics, trace-level evals; **4.0 released May 13, 2026** as an "Evaluation Harness for Vibe Coding Agents"; v4.0.3 current) ([DeepEval](https://deepeval.com/), [DeepEval 4.0](https://deepeval.com/blog/introducing-deepeval-4), [2026 changelog](https://deepeval.com/changelog/changelog-2026), [digitalapplied](https://www.digitalapplied.com/blog/ai-agent-eval-frameworks-testing-guide-2026)); `Inspect AI` v0.3.225 from the UK AI Security Institute ([digitalapplied](https://www.digitalapplied.com/blog/ai-agent-eval-frameworks-testing-guide-2026)); `Promptfoo` (now OpenAI-owned, see §3.5); plus the platform-native evals in LangSmith, Braintrust, Phoenix and Langfuse.

**Three eval layers you need** ([digitalapplied](https://www.digitalapplied.com/blog/agent-observability-2026-evals-traces-cost-guide)):
1. **Unit evals** on discrete steps
2. **LLM-as-judge regression suites** for subjective outputs
3. **Trajectory evals** over the full ordered trace — tool selection, arguments, plan, recovery, task completion. Trajectory-first evaluation is the differentiator for anything past ~3 tool calls per task ([Future AGI](https://futureagi.com/blog/agent-metrics-frameworks-2026/)).

### 3.4 Governance: approval gates, kill switches, audit logs, budget caps

The 2026 pattern is a pyramid: **visibility first (audit trails), then control (approvals, budgets, kill-switches)** ([dobby-ai](https://dobby-ai.com/academy/ai-agent-governance-best-practices)).

**Minimum bar before deploying an agent** ([nhimg](https://nhimg.org/faq/what-governance-controls-should-every-enterprise-put-in-place-before-deploying-a/)): a unique named identity per agent; every agent mapped to an accountable human owner; least-privilege scoped credentials; immutable audit trail of all actions; human-in-the-loop approval gates.

**Audit records need a schema, not logs to grep.** Minimum fields: identity (agent name, version, environment, instance ID) and caller (user/service ID, request source, session) ([onefrequency](https://www.onefrequencyconsulting.com/insights/agent-governance-at-scale-audit-logs-approval-gates)). IDC's blunt assessment: most enterprises "can't verify what their AI agents actually do," and more than a third have already deployed agents inside finance and accounting — with a proposed **AI Kill Switch Act** in play ([IDC](https://www.idc.com/resource-center/blog/the-audit-trail-that-doesnt-exist/)).

**Buyer-side pressure is now the forcing function.** By mid-2026 enterprise procurement checklists "routinely demand kill switches, evidentiary audit trails, human-in-the-loop boundaries, model change control, outcome-based SLAs, and ISO/IEC 42001 or SOC 2 attestations" ([zylos](https://zylos.ai/research/2026-07-02-buyer-side-governance-enterprise-ai-agent-deployments/)).

**HITL is an authorization problem, not a UI problem.** The critical distinction, from the emerging authorization patterns literature: "A confirmation prompt inside the agent is not authorization." Framework-level confirmations "do not by themselves constitute authorization and **MUST** be bound to a verifiable authorization grant issued by the authorization server," and the agent "**MUST NOT** treat local U[I confirmation as authorization]" ([Security Boulevard](https://securityboulevard.com/2026/08/human-in-the-loop-authorization-patterns-for-autonomous-agents/)). Design HITL with explicit approval scope, timeout behavior, exception routing and decision paths — not a single Approve button ([digitalthoughtdisruption](https://digitalthoughtdisruption.com/2026/07/12/human-in-the-loop-ai-agent-approval-paths/)), and put durable state first so a paused run can actually resume ([Michel Tricot](https://www.linkedin.com/pulse/implementing-confidence-thresholds-approval-gates-agent-michel-tricot-gwdxc)).

**Framework-level support now exists and you should use it rather than build it:**
- LangChain 1.0 **human-in-the-loop middleware** "pauses agent execution so users can approve, edit, or reject tool calls before execution," alongside summarization and PII-redaction middleware ([LangChain](https://www.langchain.com/blog/langchain-langgraph-1dot0)).
- AI SDK 6 ships **tool execution approval** ([Vercel](https://vercel.com/blog/ai-sdk-6)).
- ADK Go 2.0 ships built-in HITL with durable resume, idempotent resume, `ErrInvalidResumeResponse`/`ErrNothingToResume`, per-node retry policies (5 attempts, 1s initial, 60s cap, 2× backoff, full jitter), per-node timeouts and graph-wide concurrency limits ([Google](https://developers.googleblog.com/announcing-adk-go-20/)).
- MAF tool approval + **AG-UI** transports the approval request to the client and the decision back ([Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/ui/ag-ui/human-in-the-loop)).
- Claude Managed Agents permission policies now include **`auto`**: "the server evaluates each agent or MCP tool call and runs it, denies it, or pauses for approval," with `agent.tool_use`/`agent.mcp_tool_use` events reporting the decision in an `evaluation` field. The `ant` CLI can attach a terminal to a live session to allow/deny pending tool calls (`ant beta:sessions connect`) ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api)).
- **Config-as-code for agents:** `ant apply` (CLI 1.30.0, Sep 3 2026) "creates and updates agents, environments, skills, memory stores, and deployments from repository files," prints a plan for approval, and writes a `claude-lock.json` lockfile so CI updates rather than duplicates resources ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api)). This is the closest thing to Terraform-for-agents shipping today.

### 3.5 Agent identity & authentication

A standards consensus emerged in 2026, and it is worth adopting rather than inventing ([IDSync State of AI Agent Identity 2026](https://idsync.com/reports/state-of-ai-agent-identity-2026)):

| Layer | Standard | Status |
|---|---|---|
| **What is this agent** (workload identity) | **SPIFFE/SPIRE** — CNCF-graduated; "short-lived, attestation-based credentials instead of static secrets." 2026 reference architectures from HashiCorp, Stacklok, Teleport and Defakto put it under agent deployments. Known friction: SPIRE's pre-registration model fits long-lived services better than dynamically spawned sub-agents. | Production |
| **What is this agent** (IETF track) | **WIMSE** (Workload Identity in Multi-System Environments) — architecture draft dated **March 2026**; workload credentials, proof-of-possession tokens and agent-specific drafts active. There is still **no dedicated IETF working group for AI agents**; work is split across WIMSE and the OAuth WG. Each agent workload MUST have exactly one WIMSE identifier, which MAY be a SPIFFE ID. | Draft |
| **What may it touch** (delegated access) | **OAuth 2.1 via the MCP authorization spec** — MCP servers act as resource servers; separation required between authorization server and MCP servers; **RFC 8707** resource indicators bind tokens to specific servers. | Production |
| **Client registration** | **CIMD (Client ID Metadata Documents)** — recommended in MCP `2025-11-25`; **DCR formally deprecated** in `2026-07-28`. Anthropic's Claude connectors already support CIMD alongside legacy dynamic registration. | Migrating |
| **Enterprise brokering** | **ID-JAG (Identity Assertion Authorization Grant)** — reached **draft-04** as an adopted OAuth WG document in **May 2026** (Aaron Parecki/Okta, Brian Campbell/Ping); productized as **Cross-App Access (XAA)** for centrally brokered, revocable agent access. Okta runs an ecosystem program; Keycloak documented an implementation. | Draft, productizing |
| **Future MCP auth** | **SEP-1932 (DPoP)** and **SEP-1933 (Workload Identity Federation)** on the 2026 MCP roadmap | Proposed |

The organizing principle: **an agent is a first-class non-human identity** — "its own cryptographically-attested principal, short-lived at runtime, with the human preserved as a *separate* delegating subject" ([agentmelt](https://agentmelt.com/blog/ai-agent-identity-access-management-2026/)). Microsoft's Entra docs now carve agents out explicitly: because they make dynamic decisions, "identity must be issued per run and scoped per task" ([digitalapplied](https://www.digitalapplied.com/blog/agent-identity-credentials-non-human-access-2026-playbook)). Commercial platforms in this space: Aembit, Stytch, Nango, WorkOS FGA, CyberArk for AI ([zylos](https://zylos.ai/research/2026-04-11-agent-authentication-delegated-access-oauth-scoped-tokens/)).

**Credential-handling patterns worth copying:**
- Daytona: "Secrets keep plaintext credentials outside the sandbox and substitute them at network egress" ([Daytona](https://www.daytona.io/)).
- Vercel Sandbox: "Credentials injected on egress: never enter the sandbox" — e.g. an `api.openai.com` rule transforms the Authorization header to `Bearer $OPENAI_API_KEY` without the key existing inside the microVM ([Vercel](https://vercel.com/sandbox)).
- Anthropic Managed Agents: OAuth tokens in a secure vault; Git repo tokens injected at sandbox init so `push`/`pull` work "without the agent handling the token" ([Anthropic](https://www.anthropic.com/engineering/managed-agents)).
- OpenAI: "Separating harness and compute helps keep credentials out of environments where model-generated code executes" ([OpenAI](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)).

Network egress control is not optional.

### 4.1 Memory is now a benchmarked layer

"Memory has moved from an afterthought to its own benchmarked, actively researched layer of the stack over the past 18 months… In 2026, AI agent memory is a first-class architectural component." ([Mem0](https://mem0.ai/blog/state-of-ai-agent-memory-2026))

**The three standard benchmarks:**

| Benchmark | Composition |
|---|---|
| **LoCoMo** | 1,540 questions across single-hop, multi-hop, open-domain, and temporal memory recall |
| **LongMemEval** | 500 questions across single-session user/assistant/preference recall, knowledge update, temporal reasoning, multi-session recall |
| **BEAM** | Evaluated at **1M and 10M token scales**, across preference following, instruction following, information extraction, knowledge update, multi-session reasoning, summarization, temporal reasoning, event ordering, abstention, contradiction resolution |

Source: [Mem0](https://mem0.ai/blog/state-of-ai-agent-memory-2026)

**The metric that matters is accuracy per token.** "A system that scores well on accuracy but requires 26,000 tokens per query is not production viable." Mem0's April 2026 token-efficient algorithm (single-pass hierarchical extraction + multi-signal retrieval) self-reports:

| Benchmark | Score | Avg tokens/query |
|---|---:|---:|
| LoCoMo | 92.5 | 6,956 |
| LongMemEval | 94.4 | 6,787 |
| BEAM (1M) | 64.1 | 6,719 |
| BEAM (10M) | 48.6 | 6,914 |

Biggest gains: **+29.6 points on temporal reasoning, +23.1 on multi-hop**. Also: "Vector memory retrieves semantically similar facts. Graph-style memory retrieves facts through entities and relationships. Both are useful; neither is sufficient alone." Ecosystem: **21 frameworks and 20 vector stores** integrated, across managed cloud, OSS self-hosted, and local MCP. Hardest open problems: **cross-session identity, temporal abstraction at scale, and memory staleness**. ([Mem0](https://mem0.ai/blog/state-of-ai-agent-memory-2026), foundation paper *Mem0*, arXiv:2504.19413, ECAI 2025)

**Caveat:** these are self-reported vendor numbers published on the vendor's own research page ([mem0](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)), and competing systems (ByteRover, supermemory, MemPalace claiming 96.6% LongMemEval) report their own ([bestaiweb](https://www.bestaiweb.ai/byterover-mem0g-and-supermemory-the-2026-agent-memory-benchmark-race-on-locomo-and-longmemeval/), [rohitraj](https://rohitraj.tech/notes/open-source-ai-agent-memory-mem0-vs-zep-letta-2026)). Run your own.

### 4.3 Long context vs RAG — the settled answer

**Long context did not kill RAG; it killed *naive* RAG and moved the boundary.** ([haal-lab](https://haal-lab.solutions/en/blog/rag-vs-long-context))

Context windows in 2026: Claude Fable 5.1 and Mythos 5.1 ship a **1M token context window by default** with 128k max output ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api)). Gemini-class models sit at 1–2M ([haal-lab](https://haal-lab.solutions/en/blog/rag-vs-long-context)); Claude Opus 4.6/Sonnet 4.6 reached 1M GA on March 13, 2026 and GPT-5.4 was ~1.05M ([toolhalla](https://toolhalla.ai/blog/rag-vs-long-context-2026)).

Why retrieval survived:
1. **Cost.** "RAG can be around 1,250 times cheaper per query than stuffing a full corpus into context" ([ecorpit](https://ecorpit.com/long-context-2m-tokens-vs-rag-cost-latency-2026/)). You pay per token, every call ([agentscamp](https://agentscamp.com/guides/concepts/rag-vs-long-context.md)).
2. **Context rot.** "Effective recall on million-token prompts collapsed in the middle of the window" ([tianpan](https://tianpan.co/blog/2026-04-27-long-context-vs-rag-2026-decision-tree)).
3. **Latency, freshness, access control, citations** ([codefarm](https://codefarm.in/blog/gen-ai/long-context-vs-rag-2026), [ecorpit](https://ecorpit.com/long-context-2m-tokens-vs-rag-cost-latency-2026/)).
4. **The long-context price premium** is real — OpenAI charges 2× on long-context requests ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)).

**Decision rule:** corpus under ~100K tokens total and re-read whole → stuff it. Millions of docs, or freshness/ACL/citation requirements → retrieve. Everything in between → hybrid, decided per feature on cost, latency, freshness and citation needs ([codefarm](https://codefarm.in/blog/gen-ai/long-context-vs-rag-2026), [ecorpit](https://ecorpit.com/long-context-2m-tokens-vs-rag-cost-latency-2026/), [tianpan](https://tianpan.co/blog/2026-04-27-long-context-vs-rag-2026-decision-tree)).

### 4.4 Context engineering — the four techniques

Context engineering is "the set of strategies for curating and maintaining the optimal set of tokens during LLM inference" ([reactify](https://www.reactify-solutions.com/articles/context-engineering-ai-agents-2026)). Anthropic formalized three techniques as API primitives — **compaction**, **context editing** (`clear_tool_uses_20250919`), and the **memory tool** — plus **Skills** for progressive disclosure ([dreaming.press](https://dreaming.press/posts/context-engineering-anthropic-way-claude-skills-compaction-memory.md), [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

| Technique | What it does | Failure mode |
|---|---|---|
| **Compaction** | Runs history through an LLM and replaces prior turns with a high-fidelity summary | "Summaries drop exact identifiers, paths, and error strings needed to resume" ([gamechangerlabs](https://gamechangerlabs.io/blog/context-engineering-for-ai-agents)) |
| **Tool-result clearing / observation masking** | Drops or masks stale tool outputs. JetBrains' SWE-bench runs found **observation masking beat LLM summarization: 52% cost cut and +2.6% solve rate** | Loses detail the agent may re-need ([agentnative](https://www.agentnative.dev/patterns/context-compaction-pattern-for-long-running-agents)) |
| **External memory** | Push durable facts to files/graph so they survive summarization | Staleness ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)) |
| **Retrieval budgeting / memory tiering** | Explicit token budget per context class | Under-retrieval ([digitalapplied](https://www.digitalapplied.com/blog/context-engineering-agent-reliability-playbook-2026)) |

**Critical interaction to get right: compaction breaks prompt caches.** Cache stability and compaction are in direct tension ([zylos](https://zylos.ai/research/2026-04-21-agent-context-compaction-long-running-sessions/)) — which is exactly why MCP `2026-07-28` added deterministic ordering and cache hints on tool-list responses to "keep upstream prompt caches stable across reconnects" ([MCP](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). Use **threshold-triggered** compaction, not per-turn ([agentnative](https://www.agentnative.dev/patterns/context-compaction-pattern-for-long-running-agents)), and keep the compacted prefix stable.

Frameworks now do this for you: LangChain 1.0 summarization middleware "condenses message history as it approaches context limits, keeps recent messages intact, and summarizes older context" ([LangChain](https://www.langchain.com/blog/langchain-langgraph-1dot0)); MAF's harness "monitors token usage" and "compacts chat history mid-loop" ([Microsoft](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-at-build-2026-announce/)).

### 4.5 Knowledge graphs for agent memory

The 2026 consensus is **hybrid**: "vector memory for broad semantic recall and fast factoid lookup, a knowledge graph for multi-hop reasoning" ([Mnemoverse](https://mnemoverse.com/docs/library/knowledge-graph-memory-for-agents)). Production stacks combine skeleton-indexed knowledge graphs, temporal edges for agent memory, DRIFT search for adaptive retrieval, and A2A-coordinated agents using the graph as shared state ([Paolo Chignoli](https://www.paolochignoli.it/blog/knowledge-graphs-eating-rag-production-graphrag)). Microsoft's Agent Framework formalizes two Neo4j context-provider patterns — agent memory and GraphRAG — sharing a graph DB but using separate packages and data flows ([Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/context-providers/neo4j)). Research continues: **MemGraphRAG** introduces a memory-based multi-agent system for graph RAG quality ([arXiv:2606.00610](https://arxiv.org/abs/2606.00610)).

### 5.2 Self-improving agents

The field has a survey-level consolidation now: *Self-Improvements in Modern Agentic Systems: A Survey* (arXiv:2607.13104, July 14, 2026, Ren et al. incl. Schmidhuber), which formalizes self-improvement as "a self-induced update operator that obtains and commits updates to model parameters or scaffold components" over 200+ references ([arXiv](https://arxiv.org/abs/2607.13104), [reproduction study](https://rgv-repro-self-improvements-in-modern-agentic-systems.static.hf.space/index.html)). An earlier survey, *A Survey of Self-Evolving Agents*, was last revised January 16, 2026 ([arXiv:2507.21046](https://arxiv.org/abs/2507.21046)).

Three practical mechanisms are actually shipping:

1. **Skill libraries with RL.** SAGE (Skill Augmented GRPO for self-Evolution) enhances self-improvement with a skill library ([ACL 2026](https://aclanthology.org/2026.acl-long.69.pdf), [arXiv](https://arxiv.org/html/2512.17102v2)); SKILLRL builds a hierarchical skill library via experience-based distillation and recursive evolution ([OpenReview](https://openreview.net/pdf?id=56D2hjARkn)); SCAFFOLD induces "parametric, executable skills" for visual web agents ([arXiv:2609.05511](https://arxiv.org/html/2609.05511v1)).
2. **Eval-gated online learning.** The pattern is an evaluation function, a feedback mechanism, and continual training gated on evals — "Online Learning (eval-gated continual training)" ([Morph](https://www.morphllm.com/self-improving-ai)). Deployment-derived traces or harness-mediated signals update the model, but "this path depends on the runtime system rather than replacing it: the harness selects traces" ([OpenReview](https://openreview.net/pdf?id=IUltZSgLMm)). AREAL2.0 reorganizes RL infra into "an agent service-oriented online RL loop for policy LLM weight updates from deployed online agent workloads" ([arXiv](https://arxiv.org/pdf/2607.01120)).
3. **Product-level improvement loops.** OpenAI Presence: "Codex proposes updates that teams can test and approve, helping the agent adapt as customer behavior changes" — measured at **-15pp human handoffs in 10 days** ([OpenAI](https://openai.com/index/introducing-openai-presence/)). Arize positions itself as "The AI engineering platform for self-improving agents. Observe. Evaluate. Learn." ([Arize](https://arize.com/)). Letta's whole research agenda is here: memory-native RL, Context Constitution, continual learning in token space, sleep-time compute ([letta.com](https://www.letta.com/)).

**Note the deprecation risk:** OpenAI's fine-tuning platform "is no longer accessible to new users," with existing users able to create training jobs "for the coming months" ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)). Don't architect a self-improvement loop around OpenAI SFT/RFT right now.

### 5.3 Computer use & browser automation

The ecosystem **bifurcated** between DOM-driven (Playwright + Claude, Stagehand, Browserbase) and vision-driven (Anthropic Computer Use, OpenAI CUA) approaches; most teams default to DOM-driven for reliability and cost ([digitalapplied](https://www.digitalapplied.com/blog/browser-automation-ai-agents-playwright-stagehand-2026)).

- **Stagehand** (Browserbase, MIT) — "the only open source browser AI framework built specifically for browser agents," with four primitives: `act`, `extract` (Zod-schema structured data), `observe`, `agent`. "Instructions like 'click the submit button' survive page redesigns because they're resolved by AI at runtime, not hardcoded." Local-first with full feature parity, then "connect to Browserbase's cloud browsers with no code changes." TypeScript and Python ([Browserbase](https://www.browserbase.com/stagehand)). **v4 is a rewrite moving core execution into a native browser extension, claiming 2× Playwright speed and 80% token savings** ([4geeks](https://4geeks.com/en/blog/ai-tools/que-es-stagehand)).
- **Context-efficient browsing is the 2026 trick.** Playwright CLI's April 2026 bet: "stop streaming DOM/accessibility trees into an agent's context window through MCP tool calls, and instead persist browser state to disk as compact YAML that the agent reads on demand" ([nikiforovall](https://nikiforovall.blog/ai/2026/07/05/browser-automation-agents-ecosystem.html)).
- **Cloudflare** ships a Browser tool in the Agents SDK for page inspection, screenshots and browser tools ([Cloudflare](https://developers.cloudflare.com/agents/)); **E2B Desktop** exposes mouse/keyboard/screenshot/streaming APIs ([E2B](https://github.com/e2b-dev/E2B)).
- **Benchmark reality:** see §3.3. Short tasks ~85%; long-horizon workflows ~20%.

### 5.4 Voice & realtime agents

The latency budget is now well-characterized, and it is the whole design problem.

**LiveKit's turn breakdown:** STT ~100–200ms, streaming LLM ~300–500ms, TTS ~100–200ms, WebRTC network ~50–150ms → **practical end-to-end target 700ms–1.2s** ([MarkTechPost](https://www.marktechpost.com/2026/08/30/lowest-latency-inference-apis-for-voice-and-realtime-agents-a-time-to-first-token-ttft-first-benchmark/)).

**Pipecat co-creator Kwindla Hultman Kramer:** recommend **800ms** median voice-to-voice, 1,500ms acceptable for PoC, split roughly 200ms each across transport/media, STT+endpointing, LLM inference, TTS. **Daily:** human conversational response ≈500ms; pauses beyond **800ms** feel unnatural; ≈**700ms TTFT budget** for the text-mode LLM inside a transcription→LLM→voice harness ([MarkTechPost](https://www.marktechpost.com/2026/08/30/lowest-latency-inference-apis-for-voice-and-realtime-agents-a-time-to-first-token-ttft-first-benchmark/)).

**Platform state:** OpenAI shipped `gpt-realtime-2.1` and `gpt-realtime-2.1-mini` in **early July 2026**, and stated improved caching cut **p95 latency by at least 25% across all Realtime voice models** ([MarkTechPost](https://www.marktechpost.com/2026/08/30/lowest-latency-inference-apis-for-voice-and-realtime-agents-a-time-to-first-token-ttft-first-benchmark/), [TechTimes](https://www.techtimes.com/articles/319860/20260707/openai-realtime-api-cuts-voice-agent-latency-25-adds-reasoning-mini-model.htm)). Transports: WebRTC, WebSocket and **SIP (now GA)** ([Forasoft](https://www.forasoft.com/blog/article/openai-realtime-api-voice-agent-production-guide-2026)). Two speech-to-speech protocols dominate: OpenAI Realtime and Google's Gemini Live API (`BidiGenerateContent`) ([zylos](https://zylos.ai/research/2026-07-19-realtime-voice-api-protocol-adaptation/)). Mid-conversation tool calling keeps the 2024 function-calling contract: `tools` in `session.update`, a `function_call` output item, then `function_call_output` + `response.create` to resume ([zylos](https://zylos.ai/research/2026-07-18-realtime-voice-agent-tool-calling/)).

Cloudflare exposes voice as a first-class channel in the Agents SDK ("Build a real-time voice agent with speech-to-text and text-to-speech") ([Cloudflare](https://developers.cloudflare.com/agents/)), and Pydantic AI now advertises "Agents, realtime voice" in its tagline ([GitHub](https://github.com/pydantic/pydantic-ai)). OpenAI Presence "supports real-time experiences across voice and chat" ([OpenAI](https://openai.com/index/introducing-openai-presence/)).

### 5.6 Agent Skills as a portability standard

Anthropic released **Agent Skills** as an open standard on **December 18, 2025** at **agentskills.io**: a folder with `SKILL.md`, YAML frontmatter (`name`, `description`, optional `allowed-tools`, `model`), markdown instructions, and optional `scripts/`, `references/`, `assets/`. Progressive disclosure means only relevant context enters the window ([getclaudeskills](https://www.getclaudeskills.com/blog/agent-skills-in-2026-state-of-the-ecosystem), [paperclipped](https://www.paperclipped.de/en/blog/agent-skills-open-standard-interoperability/), [Anthropic](https://claude.com/blog/skills)).

Adoption is genuinely cross-vendor: Microsoft integrated it into VS Code within 48 hours ([paperclipped](https://www.paperclipped.de/en/blog/agent-skills-open-standard-interoperability/)); Copilot, Cursor, VS Code, Gemini CLI and Codex read `SKILL.md` ([agentscamp](https://agentscamp.com/guides/skills/agent-skills-open-standard)); 40+ platforms use the format ([Atlan](https://atlan.com/know/ai-agent/ai-agent-skills/what-are-agent-skills/)); MAF ships `AgentSkillsProvider` ([Microsoft](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-at-build-2026-announce/)); the OpenAI Agents SDK harness supports "progressive disclosure via skills" and `AGENTS.md` custom instructions ([OpenAI](https://openai.com/index/the-next-evolution-of-the-agents-sdk/)); Mastra shipped Filesystem Skills for Workspaces Sep 11, 2026 ([mastra.ai](https://mastra.ai/)); Promptfoo ships skills ([Promptfoo](https://www.promptfoo.dev/docs/integrations/agent-skill/)); Anthropic maintains a public `skills` repository ([AIToolly](https://aitoolly.com/ai-news/article/2026-08-15-anthropic-launches-public-agent-skills-repository-for-claude-to-standardize-ai-agent-capabilities)). Skills and the Skills API (`/v1/skills`) are **out of beta on the Claude API** ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api)). And `AGENTS.md` itself is now hosted by AAIF ([Forbes](https://www.forbes.com/sites/janakirammsv/2026/08/19/agent2agent-joins-the-agentic-ai-foundation-alongside-mcp/)).

**Practical takeaway:** write your agent's procedural knowledge as `SKILL.md` files in your repo. It is the only agent asset that is portable across OpenAI, Anthropic, Microsoft and Google harnesses today.

### 6.2 Model routing tiers (concrete, September 2026)

Put three tiers behind the gateway, route on task complexity, then measure. All prices per 1M tokens, from the vendors' own pricing pages.

| Tier | Use for | OpenAI ([pricing](https://developers.openai.com/api/docs/pricing)) | Anthropic ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)) |
|---|---|---|---|
| **Cheap / high-volume** | Classification, routing decisions, extraction, summarization, guardrail checks, memory extraction, tool-arg validation | `gpt-5.6-luna` — **$0.20** in / **$0.02** cached / **$1.20** out | **Claude Haiku 4.5** — **$1** in / **$0.10** cache hit / **$5** out |
| **Workhorse** | Most agent turns, tool selection, drafting, RAG synthesis | `gpt-5.6-terra` — **$2.00** / **$0.20** / **$12.00** | **Claude Sonnet 5** — **$2** / **$0.20** / **$10** |
| **Frontier / escalation** | Long-horizon planning, hard debugging, adversarial review, final QA gate | `gpt-5.6-sol` — **$4.00** / **$0.40** / **$20.00** (promotional through at least Nov 21, 2026); `gpt-6-astra` — **$10** / **$1** / **$50** | **Claude Opus 5** — **$5** / **$0.50** / **$25**; **Claude Fable 5.1** — **$10** / **$0.25** / **$50** |

Notes that materially change the math:

- **Claude Fable 5.1's cache reads are $0.25/MTok — 0.025× base input, versus 0.1× on every other Claude model.** For a long-running agent that re-reads a large stable prefix on every turn, Fable 5.1 can be *cheaper per turn* than Opus 5 despite a 2× higher headline input price. It also ships a **1M token context window by default and 128k max output** ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api), [Claude Fable](https://www.anthropic.com/claude/fable)).
- **OpenAI charges a long-context tier.** Above the short-context threshold, `gpt-5.6-sol` doubles to $8 in / $30 out. Context bloat is now a step-function cost, not a linear one ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)).
- **`tool_choice: "any"` and `"tool"` return a 400 on Fable 5.1 / Mythos 5.1.** If your TS code force-calls a tool, migrate to strict tool use / structured outputs before switching models ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api)).
- **Thinking blocks are model-bound.** For accounts created on/after Aug 31, 2026, replaying a thinking block after changing the system prompt, tools, or an earlier message returns a 400. Multi-model agent loops that shuttle history between Claude versions will break unless you handle `input_transformations` ([Anthropic release notes](https://docs.anthropic.com/en/release-notes/api)).
- Routing is worth real money — reported reductions cluster at **40–85%** for tuned routing layers and **20–80%** for intelligent request routing ([digitalapplied](https://www.digitalapplied.com/blog/llm-model-routing-2026-cost-quality-optimization-engineering-guide), [agentmarketcap](https://agentmarketcap.ai/blog/2026/04/08/agent-request-routing-multi-model-orchestration-litellm-openrouter)) — but caching is the bigger lever: **41–80% cost reduction and 13–31% better TTFT** measured across four models by PwC researchers ([arXiv:2601.06007](https://arxiv.org/html/2601.06007v2)).

### 6.3 Concrete implementation notes for Next.js

1. **Never run the agent loop inside a normal route handler.** Wrap it in a Workflow (`withWorkflow` from `workflow/next`) so each tool call is a retryable, observable, suspendable step. Workflows suspend without consuming compute while waiting ([vercel/workflow](https://github.com/vercel/workflow)).
2. **Stream with `streamText` / typed UI streams from AI SDK 6**, and use its **tool-execution approval** for the human-in-the-loop surface rather than building an approval table yourself ([Vercel](https://vercel.com/blog/ai-sdk-6)).
3. **Treat approval as authorization, not UX.** A confirmation prompt inside the agent "does not by [itself] constitute authorization and MUST be bound to a verifiable authorization grant issued by the authorization server" — so the approve/deny decision must be enforced server-side against a real grant, not a client boolean ([Security Boulevard](https://securityboulevard.com/2026/08/human-in-the-loop-authorization-patterns-for-autonomous-agents/)).
4. **Keep credentials out of the sandbox.** OpenAI's own guidance is that "separating harness and compute helps keep credentials out of environments where model-generated code executes," and that you should design assuming prompt-injection and exfiltration attempts. Vercel Sandbox's Credentials Brokering implements exactly this — the secret is injected on egress and never enters the microVM ([OpenAI](https://openai.com/index/the-next-evolution-of-the-agents-sdk/), [Vercel Sandbox](https://vercel.com/sandbox)).
5. **Default-deny egress from the sandbox,** then allowlist. Vercel Sandbox supports `allow-all` / `deny-all` / user-defined rules with live policy updates and per-domain proxying ([Vercel Sandbox](https://vercel.com/sandbox)).
6. **Budget-cap every run.** Per-run token ceiling, per-run dollar ceiling, retry cap (≈3), step limit (10–50), and a wall-clock timeout — the agent terminates on breach. Published guardrail ranges: 50K–500K tokens and $0.10–$10.00 per run ([FinOps LLM](https://finopsllm.com/research/agent-spend-guardrails-production)).
7. **Compact, don't truncate — and keep identifiers verbatim.** Summaries famously drop exact paths, IDs and error strings needed to resume; JetBrains found observation *masking* beat LLM summarization on SWE-bench runs (52% cost cut, +2.6% solve rate) ([agentnative](https://www.agentnative.dev/patterns/context-compaction-pattern-for-long-running-agents), [gamechangerlabs](https://gamechangerlabs.io/blog/context-engineering-for-ai-agents)).
8. **Design cache-first.** Put the stable system prompt, tool schemas and skills at the front; put dynamic content at the end; never inject timestamps or per-request IDs into the cached prefix. That single discipline is what turns the 41–80% caching saving on or off ([arXiv:2601.06007](https://arxiv.org/html/2601.06007v2), [digitalapplied](https://www.digitalapplied.com/blog/prompt-caching-economics-cache-first-agent-architecture-2026)).
9. **Instrument with OTel `gen_ai.*` from day one**, exporting to Langfuse (or anything else). The conventions are still marked experimental but they are the de facto wire format, and they mean you can change backends later without re-instrumenting ([agentmarketcap](https://agentmarketcap.ai/blog/2026/07/13/opentelemetry-genai-semantic-conventions-agent-observability-standard), [greptime](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)).
10. **Pin your MCP client to the `2026-07-28` spec and drop session assumptions.** No `initialize`, no `Mcp-Session-Id`; each request self-describes via `_meta`; list responses carry cache hints and deterministic ordering so your upstream prompt cache stays stable across reconnects ([MCP](https://blog.modelcontextprotocol.io/posts/2026-07-28/)).
11. **Add `AGENTS.md` and version-matched docs to the repo.** Next.js ships version-matched documentation inside the `next` package specifically so coding agents stop hallucinating old APIs, and 16.2 ships `AGENTS.md` in `create-next-app` plus `next-browser` and browser log forwarding for agent debugging ([Next.js](https://nextjs.org/docs/app/guides/ai-agents), [Next.js 16.2](https://nextjs.org/blog/next-16-2-ai)).

### 6.4 Suggested build order

| Phase | Ship | Rationale |
|---|---|---|
| 1 | AI SDK 6 `ToolLoopAgent` + 3–5 hand-written tools + Langfuse tracing + a 20-case eval set | You cannot improve what you cannot see, and 5 tools beats 40 |
| 2 | Workflow SDK durability + tool-execution approval on every destructive tool + per-run budget caps | This is the demo→production boundary |
| 3 | Vercel Sandbox with default-deny egress + credentials brokering for any code execution or file work | Treat model output as hostile |
| 4 | AI Gateway routing rules with the three-tier model ladder + cache-first prompt layout | Where the 40–80% savings live |
| 5 | MCP (`2026-07-28`) for external tools; Code Mode once you pass ~15 tools | Context economy |
| 6 | pgvector memory + Anthropic memory tool; add Mem0 or Zep only if cross-session recall becomes the bottleneck | Don't buy a memory platform before you have a memory problem |
| 7 | Promptfoo red-team suite in CI; agent identity via OAuth 2.1/CIMD; immutable audit log; kill switch | Governance before scale, not after |
| 8 | Only then consider multi-agent | "A single agent often matches or beats a multi-agent system" ([munderdiffl](https://munderdiffl.in/blog/multi-agent-orchestration-patterns/)) |
