## Discovery: where a model name comes from, per call (read before any test)
- Seats: `apps/web/lib/model-gateway.ts` `executeSeatModel` -> `resolveModelName(route.modelTier,
  provider)` per attempt, and reports THAT name as the result's `model` (-> `step_end.step.model`
  -> `wireRunSpend` -> the ledger row's `model`). `resolveModelName` (`apps/web/lib/ai-client.ts:55`)
  reads `GOOGLE_*`/`MISTRAL_*` from env PER CALL, but OpenAI and Anthropic names come from `MODELS`,
  which is FROZEN when ai-client.ts is first evaluated. The seat's input has no model field;
  `modelPolicy` routes providers only.
- Planner, critic: `orchestrator-runtime.ts` `callJson(PLANNER_MODEL|CRITIC_MODEL, ...)` with the
  wrapper's `createCompletion` port, which ignores the name and calls `gateway.complete({ role:
  "planner" })`. Consolidator (Google): the wrapper's `consolidateWithGateway` (`role: "executor"`).
  The gateway routes by `routeWorkbenchStream(role, policy)`: explicit model =
  `WORKBENCH_PLANNER_MODEL`/`WORKBENCH_EXECUTOR_MODEL` when it names the provider, else
  `resolveModelName("opus", provider)` = `<PROVIDER>_MODEL_STRONG`. The policy snapshot
  (`MODEL_PREFERRED_PROVIDER`, `MODEL_ALLOWED_PROVIDERS`) is frozen once per gateway, and the
  orchestrator builds ONE gateway per process (`index.ts` `loadGateway`).
- No per-run model seam in the app: `launchOrchestration(opts)` takes companyId, objective, trigger,
  fullTeam, cycleKind; `orchestrator-runtime.ts` freezes `PLANNER_MODEL`/`SPECIALIST_MODEL`/
  `CRITIC_MODEL` at module load; `agent-routing-context.ts` renders seat tier LABELS only. So option
  (b) has nothing to pass a model into; the only per-call input is the process environment.

## Decision: (a), a pinned run is its own process with the pin written over every model variable
1. Evidence: every model name in a run (seat, planner, critic, consolidator) is resolved from
   process env, OpenAI/Anthropic names freeze at first import, and the gateway's provider policy
   freezes once per process; nothing in apps/web takes a model per run.
2. So an in-process per-run model is impossible for two providers and a race for the others (the
   gateway and REPL share one env across `max_concurrent_runs`); a per-run process is exact for all.
3. `trent run` already is one process per run: the pin is written before the runtime is built, and a
   pinned cron job runs `trent run --model <id>` as a child and folds its event stream into the row.
- (b) rejected: it needs edits to `orchestrator/index.ts` (497 lines; P2-8 editing), the ports and
  apps/web, and still could not change the frozen OpenAI/Anthropic names or make the app's reported
  `model` honest.

### What the pin writes (orchestrator/model-env.ts, `ModelEnvConfig.pin`)
Overwritten, operator values included (the pin is more specific than both config and env):
the provider's tier variables (FAST/DEFAULT/STRONG, and `OPENAI_MODEL_CRITIC`),
`WORKBENCH_PLANNER_MODEL`, `WORKBENCH_EXECUTOR_MODEL`, `MODEL_PREFERRED_PROVIDER`, and, unless
`models.fallback_on_pin` is true, `MODEL_ALLOWED_PROVIDERS=<provider>` so neither the seat loop nor the
gateway can answer from another provider's model (P1-C's rule, applied to every call of the run).
An alias provider (ollama, lmstudio, deepseek, groq) writes the OpenAI names; openrouter derives seat
names from the Anthropic table with an `anthropic/` prefix, so an `anthropic/<m>` pin writes `<m>`
there, and any other openrouter pin is refused (CONFIG) because a seat could not run on it.
The pin names a model of the profile's provider; a model the provider does not serve fails with the
provider's own error, never on another model.

### The run side
- `HeadlessRuntimeDeps.model` (the process's pin) reaches `createOrchestrator` as `model.pin`.
- `HeadlessRunOptions.model` (one run's model): a runtime runs on ONE model per process, so a run
  naming a model other than the runtime's pin is refused (CONFIG) before the orchestrator is called.
  That makes the runtime the enforcement point: an in-process caller that forwards a pin (the
  service daemon's cron runner) can never run a pinned job on another model.
- `trent run --model <id>`: pin in the runtime deps and in the run options; the `system` line and the
  `result` carry `model` (what was asked) and `models` (the distinct `step.model` values the events
  carried, i.e. what ran).
- Cron: a pinned prompt job runs `trent --profile <p> run - --model <id> --format stream-json` in a
  child, prompt on stdin (never argv: `ps` shows argv, and a prompt beginning `-` would parse as a
  flag), env `TRENT_RUN_SURFACE=cron` so the child's ledger rows are cron's and its trigger is
  `scheduled`. The child's lines are the run bus's own `OrcEvent`s, folded by the same `fold`; a
  `result` whose status is not `completed` fails the row with the result's `error`. The child
  registers itself as a live writer (`createHeadlessRuntime` -> `acquireProfileWriter`), the parent
  keeps its own registration (runtime, or `start()`), so maintenance still refuses while either is up.
  `refusePin` and its test are deleted.
