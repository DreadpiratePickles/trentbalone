## The public API (for S2/S3)
`createSoloRunner(deps: SoloRunnerDeps): SoloRunner` (`solo/runner.ts`, barrel `solo/index.ts`).
- deps: `gateway` ({complete}), `tools` ({adapters}: a `TrentToolBuild`), `session` ({history, append}:
  history is AFTER compaction), `memory` ((req) -> {stable, context} ContextBlocks), `meter`
  ({open?, record -> cents, stopReason?, close?}), `checkpoints?` ({beginTurn}), `now?`,
  `config?` ({maxToolCalls=25, model (pin), temperature, maxTokens, ceilingChars}), `profileDir?`
  (persona), `workspace?`, `companyId?` (the adapters' `{companyId}` payload), `humanAnswers?`, `newId?`.
- `SoloRunner` = `AgentRunner` + `approve(runId, stepId)`, `reject(...)`, `answer(runId, stepId, text)`
  (the orchestrator's signatures: it IS the REPL's `bindApprovalAnswers` target and the gateway's
  `linkRunApprovals` target), `resume(runId, {signal?})`, `parked()`.
- `createRunLedgerMeter({surface, companyId, perRunCapCents, dailyCapCents, ledger, now})`: the real meter
  over `orchestrator/run-hooks.ts` (open/record/close the run scope; one ledger row per model, seat trent).
- Step id is `<runId>-trent`; run ids `solo_<base36 time>_<hex>`.

## The one-tool OrcEvent sequence (asserted in runner.test.ts)
run_start {run: id, objective, status running} -> step_start {step: id, title, agentRole trent, running}
-> step_output {step.toolCalls: [read_file completed]} -> step_output {step.output: answer, toolCalls}
-> step_end {status completed, model, tokens, costCents} -> run_done {run.summary: answer}.
A held call: ... -> step_output {toolCalls: [..., needs_approval]} -> step_awaiting_approval ->
run_awaiting_approval (title = the held call, detail = the held record's summary) and the stream ends
(fold: input-required) unless a decision arrived before the next pull, in which case step_approved and
the loop continue in the same stream.

## Follow-ups for S2/S3 (not done here, by scope)
1. S3: the brain block renders `brain/system/` in full, so `solo.md` would appear twice (persona AND
   brain block). The S3 memory adapter should pass `excludeSystemFiles: ["solo.md"]` to
   `renderBrainBlock` (`fleet-memory/brain-prompt.ts` already has the option).
2. S3: parked state is in-process (`runs` map in the runner); a restart abandons a parked solo run (its
   hold stays in the transcript). Durable resume needs the parked state in the session.
3. S2: `agent.mode` is validated but read by nothing; `agent.max_tool_calls` does not exist (the runner
   takes `config.maxToolCalls`). The REPL must not also thread `history` into a solo run: the runner owns
   the session through its port.
4. S2: the gateway/A2A decide after the stream ended, so they must call `resume(runId)` after
   `approve`; the REPL's in-stream decision needs nothing extra.
5. The system prefix is frozen per runner (= per session): a memory write in turn 1 reaches the
   prompt in the next session, as Hermes does, by design (P2-7).
