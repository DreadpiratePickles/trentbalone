## Facts established before changing anything
- `tools/mcp/client.ts` `connectHttp`: an http server's credential is a `${ENV}` header template, resolved from
  the env handed to `connect`. Through the egress proxy every request carries `x-trent-own-credential: 1`
  (P2-14), so the broker never swaps the model key in.
- `tools/web/proxied-fetch.ts` `createEgressFetch` follows redirects itself and re-sends the SAME headers on
  every hop, cross-origin included (lines 187-202). An MCP server that answers 307 to another host would hand
  that host the configured `Authorization` header. It checks the SSRF floor on redirect hops only; the first
  hop is the caller's to check.
- `egress/CredentialBroker.ts` `applyCredentials`: a request through the proxy WITHOUT the own-credential
  marker gets `Authorization: Bearer <record secret>` (in the REPL, the model provider key). Every OAuth
  request (metadata, registration, token) that goes through the proxy must therefore carry the marker too,
  or the authorization server receives the model key.
- `@modelcontextprotocol/sdk` 1.30.0 ships `client/auth.js`. Measured against 2026-07-28 it misses MUSTs:
  it proceeds when `code_challenge_methods_supported` is absent (auth.js:696), never checks the metadata
  `issuer` against the URL it was built from (auth.js:607-640), falls back to "the MCP server's origin is the
  authorization server" when protected-resource metadata is missing (auth.js:672-676, the 2025-03-26
  behaviour), and has no RFC 9207 `iss` check. Its transport runs the browser flow from inside a request,
  which a seat or a cron job must never do. Decision: implement the client side here, reusing
  `connect/oauth.ts` (`pkcePair`, `randomUrlToken`), `connect/loopback.ts` (`startLoopback`),
  `connect/lock.ts` (`withRefreshLock`) and `ConfigManager.saveSecrets`, and keep the SDK for the transport.
- `apps/cli/src/commands/groups/mcp.ts` connects with `{ env: process.env }` and no egress, so from the CLI an
  http server is always "egress proxy is not running" (pre-existing). The login is an interactive,
  user-started action like `trent connect`, so it runs with the process fetch and the SSRF floor on every
  URL; the MCP data path keeps "no direct mode".
- `doctor/checks/mcp.ts` reads `<profile>/mcp.json` or `mcp.servers`, never the `mcp_servers` block
  `trent mcp add` writes (pre-existing; reported, not rewritten: this task owns the message only).
- `docs-truth.test.ts` counts commands against README ("35 commands, 151 with their subcommands"); README is
  not this task's. The surfaces are therefore flags: `trent mcp add ... --oauth`, `trent mcp test <name>
  --oauth`, and the auth state on `trent mcp list`. No new subcommand, so no README line changes.

## Spec version and RFCs implemented
MCP authorization, revision **2026-07-28** (`/specification/latest` resolves there on 2026-09-26). The SDK
Trent's transport runs on (`@modelcontextprotocol/sdk` 1.30.0) negotiates protocol `2025-11-25`
(`LATEST_PROTOCOL_VERSION`); the authorization layer is Trent's own and follows 2026-07-28.
RFC 6750 s.3 (Bearer challenge), RFC 9728 (protected-resource metadata, s.3.3 resource check), RFC 8414 +
OIDC Discovery 1.0 in the spec's order with the `issuer` identity check, RFC 7636 (S256 only; absent
`code_challenge_methods_supported` refuses), RFC 7591 (native public client, `application_type: native`),
RFC 8707 (canonical `resource` at authorize, token and refresh), RFC 9207 (`iss` on the callback), RFC 8252
s.7.3 (the `trent connect` loopback listener), OAuth 2.1 refresh with rotation kept.
Not implemented, by decision: Client ID Metadata Documents (Trent hosts no HTTPS client document),
pre-registered client entry, step-up on 403 `insufficient_scope`.
