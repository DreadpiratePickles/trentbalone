- The untrusted tag: business reads set `provenance: "untrusted"` on a record, which
  `PolicyDispatcher` turns into an `inbound` entry of the run's ring, which `send-after-untrusted`

  the run's ring with one `inbound` entry through public API (`runWithToolCallContext` +
  `PolicyDispatcher.remember`) on the run's first frame, and prefixes the first message with the
  memory hold's marker `[provenance: untrusted via webhook:<route>]` (the prefix auto-review reads).

## Open, for other owners
- S2: `HeadlessRuntime` exposes the runner of its own mode only, so a route whose `mode` differs from
  `agent.mode` is answered 503 by `trent gateway start`. A `runnerFor(mode)` on the runtime makes it
  work with no engine change (the servers.ts hunk passes `runnerFor`).
- S2 (+ tools owner): the runtime does not expose the `PolicyDispatcher` its tools were wrapped with
  (`buildTrentTools` creates it; `TrentToolBuild`/`ToolWiring` do not return it), so the CLI passes
  no `seedInbound` and a webhook run's ring is not seeded from `gateway start`. With it exposed, the
  servers.ts hunk gains one line: `seedInbound: (runId, source) => seedInboundTaint(<policy>, runId, source)`.
  Sends still ask a human at every level (the class floor), and the first message carries the marker.
- H1: auto-review reads the approval row's preview/action/args only, so a bound send from a
  webhook-started run carries no untrusted marker there; H1 may want the bound row to record the
  run's inbound seed (or the send-after-untrusted rule id) so auto-review refuses it.
